## Versioning

Las versiones oficiales utilizarán Semantic Versioning:

```text
MAJOR.MINOR.PATCH
```

Ejemplo:

```text
1.0.0
```

Donde:

- **MAJOR** → cambios importantes en la estructura o filosofía del Mastery.
- **MINOR** → nuevos módulos, Labs, Projects o funcionalidades.
- **PATCH** → correcciones, mejoras menores o ajustes de documentación.

Mientras el repositorio se encuentre en construcción, los cambios permanecerán principalmente dentro de:

```text
[Unreleased]
```

## Change Types

Cuando corresponda, los cambios se organizarán utilizando las siguientes categorías:

### Added

Nuevo contenido, herramientas, Labs, Projects o funcionalidades.

### Changed

Cambios importantes sobre contenido o configuraciones existentes.

### Deprecated

Contenido o herramientas que siguen disponibles, pero dejarán de recomendarse.

### Removed

Contenido, configuraciones o herramientas eliminadas.

### Fixed

Correcciones de errores técnicos, documentación o ejemplos.

### Security

Cambios relacionados con seguridad, dependencias o configuraciones vulnerables.

## Release Philosophy

No se creará una nueva versión por cada archivo Markdown agregado.

Las versiones representarán hitos relevantes dentro de la evolución del Mastery.

Por ejemplo:

```text
0.1.0 → Foundations completed

0.2.0 → Project tooling completed

0.3.0 → Build and automation completed

0.4.0 → Monorepo tooling completed

1.0.0 → Developer Tooling Mastery completed
```

El objetivo del Changelog es registrar la evolución significativa del repositorio sin convertirlo en un historial detallado de cada commit.
